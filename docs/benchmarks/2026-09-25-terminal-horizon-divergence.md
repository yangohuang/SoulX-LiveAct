# Why matched 30/90-second LiveAct clips diverge near the short request's end

The [exact-audio-condition study](2026-09-25-exact-audio-conditioning-horizon.md) found that a continuous 90-second video and a fresh 30-second video used the same canonical 30-second BF16 audio feature tensor and seed, yet their encoded videos matched for only the first 662 of 722 common frames. The SyncNet late-trend screen remained negative; this follow-up investigates the endpoint mismatch instead of treating it as a history-quality signal. Its [bounded design](../superpowers/specs/2026-09-25-terminal-horizon-divergence.md) separates raw model output from H.264 coding and audio-window clamping.

## Existing-video and code-path audit

The [original framewise comparison](artifacts/2026-09-25-exact-audio-conditioning/liveact-exact-embedding-first30-frame-comparison.json) shows first decoded-pixel divergence at frame **662**; the last 60 frames average 3.668/255 RGB MAE. Both MP4s were encoded by Diffusers' `export_to_video` through imageio/libx264 with quality 5. FFmpeg muxes the original request audio while copying the video stream.

As a codec-only control, we decoded the **same** archived 90-second MP4 and separately re-encoded its first 722 frames versus all 2162 frames with `ffmpeg -c:v libx264 -crf 25 -pix_fmt yuv420p`. The [pairwise frame record](artifacts/2026-09-25-terminal-horizon-divergence/codec-only-comparison.json) shows the first **682/722** frames pixel-identical, then a last-40-frame mean MAE of 0.894/255. Since the encoder source pixels are identical by construction, clip length alone can change decoded tail pixels. This control uses already-compressed source frames and FFmpeg CLI rather than Diffusers' original imageio process, so its onset/magnitude cannot be directly subtracted from the original 30/90 difference.

The generator calls `get_audio_emb` on a **53-frame block window**, each frame with ±2 feature frames. [Index-level replay through the actual helper](artifacts/2026-09-25-terminal-horizon-divergence/audio-window-index-audit.json) using unique frame IDs shows the 30- and 90-second window indices equal for blocks 0–21. At block **22**, whose decoded output begins near frame **693**, 25 of 265 feature positions differ: the 30-second tensor clamps to frame 719, whereas the 90-second tensor reads the next repeated period. This identifies a real request-length conditioning difference at the final block; it does not by itself prove the corresponding real Wav2Vec feature values or model outputs differ. The original encoded-pixel onset at 662 precedes this block, consistent with encoder lookahead, but original pre-encoder frame hashes were not archived.

## Instrumented short-pair tests

The new default-off `--frame_audit` writes per-block SHA-256 of the actual audio-window tensor, initial seeded noise, final latent and decoded block, plus per-frame SHA-256 after the exact RGB float-to-uint8 conversion given to the H.264 writer. It stores hashes and shapes, not feature tensors. With image 2, seed 43, 416×720 at 24 FPS, three steps, FP8 GEMM/KV and CPU offload, `resident_kv_steps=1`, no anchor/pin/compile and disabled cuDNN benchmark, two paired runs reuse a canonical 5-second or 10-second source feature period.

For 5 versus 10 seconds, the first four block-audio, initial-noise, final-latent and VAE-decoded-block hashes match, as do all **117/117 pre-encoder frame hashes**. Yet the encoded MP4s match for only **78/117** frames; the last 40 decoded frames average 1.647/255 RGB MAE. Thus this short case demonstrates a pure output-encoder endpoint effect in the actual LiveAct export path. It does not explain all of the original 30/90 difference. The predeclared 10/20-second follow-up tests whether the final-block audio-window clamp also changes raw model output.

The audit itself has a useful no-change check: this audited 5-second MP4 and the earlier same-settings [unaudited smoke MP4](artifacts/2026-09-25-exact-audio-conditioning/liveact-exact-embedding-smoke.mp4) have the **identical SHA-256** `9b177bfd9869110ac9e19546bab967ded1d3ce4833ee0fb53edb757767b63997`. The command records differ only in the generated request/output paths and audit flag. This verifies the instrumentation did not change that short generated video on this machine, though it does not establish zero timing overhead.

The [5/10 audit comparison](artifacts/2026-09-25-terminal-horizon-divergence/audit-5-vs-10.json) uses the same canonical 120×12×768 BF16 source period in both arms; the 10-second target tiles it twice. The [MP4 comparison](artifacts/2026-09-25-terminal-horizon-divergence/short-pair-mp4-comparison.json) records the framewise differences. Both source and repeated request WAV hashes, feature sidecars, raw block/frame hashes, resource samples, logs and [short](artifacts/2026-09-25-terminal-horizon-divergence/liveact-terminal-audit-short5.mp4)/[long](artifacts/2026-09-25-terminal-horizon-divergence/liveact-terminal-audit-long10.mp4) MP4s are archived.

For 10 versus 20 seconds, the canonical source is the exact 10-second PCM WAV repeated twice in the request, and both arms encode the **same** 240×12×768 BF16 feature period (SHA-256 `192ba670e85f05a2630af10f1262d9e9c0f9becdcf566d4f0dbcc42d3d96e77d`). The [block/frame comparison](artifacts/2026-09-25-terminal-horizon-divergence/audit-10-vs-20.json) finds all four block fields equal for blocks 0–6. At **block 7**, the audio-window hash first differs while the initial seeded noise remains identical; the final latent and VAE-decoded-block hashes first differ at that same block. RGB exporter-input frame hashes are equal through frame **212**, then first differ at **213**, exactly the block's predicted first output frame. The [encoded-MP4 comparison](artifacts/2026-09-25-terminal-horizon-divergence/clamp-pair-mp4-comparison.json) instead first differs at frame **178**, 35 frames earlier. The [timeline](artifacts/2026-09-25-terminal-horizon-divergence/divergence-timeline.png) makes the raw-versus-encoded onset visible. The two playable MP4s are [10 seconds](artifacts/2026-09-25-terminal-horizon-divergence/liveact-terminal-clamp-short10.mp4) and [20 seconds](artifacts/2026-09-25-terminal-horizon-divergence/liveact-terminal-clamp-long20.mp4).

| Pair | Shared canonical feature | First different block audio | First different seeded noise | First different final latent / decoded block | First different pre-encoder frame | First different MP4 pixel frame |
|---|---|---:|---:|---:|---:|---:|
| 5 s versus 10 s | 120 frames, exact SHA match | none of 4 | none of 4 | none of 4 | none of 117 | 78 |
| 10 s versus 20 s | 240 frames, exact SHA match | **7** | none of 8 | **7 / 7** | **213** | **178** |

The second pair demonstrates a model-side endpoint effect in addition to a video-encoder effect. The short 10-second run's last 53-frame `get_audio_emb` block window clamps 25/265 selected positions to its terminal feature; the 20-second run supplies next-period features there. Because block noise and earlier blocks match, the changed final latent is consistent with this changed audio condition. The source-period feature hashes and no-flag deterministic controls rule out a different source Wav2Vec encoding as the explanation in this short pair. The MP4 onset preceding the first changed exporter-input frame is a direct warning: an encoded-video diff can mark an earlier frame than the actual model divergence.

**Conclusion and scope.** The original 30/90-second pair has the same 25/265 final-block index mismatch, and its encoded-video onset (662) is before that block's predicted raw-output boundary (693), a 31-frame lead similar to the instrumented short pair's 35-frame lead. These converging checks support a combination of terminal audio-window clamping and H.264 lookahead as the likely explanation. We cannot prove the original long-run raw frames' first mismatch without their missing pre-encoder hashes, nor can we assign a precise percentage of original RGB MAE to each mechanism from the codec-only control. This is a methodology and streaming-boundary finding, **not** evidence of accumulated long-history failure or a quality fix. For future long-form comparisons, compare feature-window and pre-encoder frame hashes, exclude/standardize request endpoints, and use decoded MP4 differences only with an encoder control.
