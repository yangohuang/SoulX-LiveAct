# LiveAct audio lookahead and repeated-period block phase

This read-only audit complements the [exact-feature 90-second negative screen](2026-09-25-exact-audio-conditioning-horizon.md) and the [request-end divergence attribution](2026-09-25-terminal-horizon-divergence.md). It quantifies the implementation's audio availability and block-grid geometry for a Vivix-style streaming-video discussion. It does **not** measure interactive latency, prove accumulated history error or run another GPU experiment. The [frozen design](../superpowers/specs/2026-09-25-liveact-audio-lookahead-phase.md) and [read-only analyzer](../../audio_block_timing.py) make its assumptions explicit.

## Block audio availability versus compute

At 24 FPS the first latent block has 6 latent frames and decodes to 21 output frames; subsequent blocks have 8 latent frames and decode to 32 output frames (1.333 seconds of video). `generate.py` forms a **53-center-frame** audio tensor for each block, and `util_liveact.get_audio_emb` selects ±2 feature frames around each center. The optional `--steam_audio` branch slices source PCM through `audio_end_idx+2` before SoX/Wav2Vec. The table describes the **input availability requested by this implementation**, not the true learned audio receptive field or a measured end-user latency.

| Block | Output frames | Unclamped selected audio-feature indices | PCM slice end, exclusive | Slice-end lead over first output |
|---|---:|---:|---:|---:|
| First, index 0 | 0–20 | −2…54 (negative positions clamp to 0) | 55 / 24 = 2.292 s | **2.292 s** |
| Later, index 1 | 21–52 | −2…54 | 55 / 24 = 2.292 s | **34/24 = 1.417 s** |
| Later, index 22 in a 30-s request | 693–724 before final mux | 670…726 (terminal positions clamp to 719) | 727 / 24 = 30.292 s | **1.417 s** |

For a later block, the same slice end is 3/24 = 0.125 seconds beyond its **last** output frame. Requiring all audio for a 32-frame block before emitting its first frame creates a 1.417-second source-audio lookahead in this schedule; a different incremental scheduler could change that. On the actual single-4090 90-second run, the later-block median was **19.161 seconds** to generate 32 frames, or **1.67 generated FPS**, roughly 14.37× slower than the 1.333 seconds of video produced. Startup, SoX/Wav2Vec, final encoding/mux and downstream interaction add more time; this is not an end-to-end latency measurement. On this machine compute dominates the stated audio-availability lead.

The measured 90-second invocation used the **non-streaming** path, which loads and encodes the complete request WAV before any video block. The 1.417-second figure is therefore a block-level data-dependency bound inferred from the streaming branch, not the latency actually delivered by the tested CLI. A truly interactive path would need incremental arrival/scheduling and separate end-to-end measurement.

The archived [30-s request](artifacts/2026-09-25-audio-lookahead-phase/period30s-x1.json) predicts 23 blocks/725 pre-encoder frames; the MP4 has 722 after `ffmpeg -shortest` against 30.000-second audio. The [90-s request](artifacts/2026-09-25-audio-lookahead-phase/period30s-x3.json) predicts 68 blocks/2165 pre-encoder frames; its MP4 has 2162. Both final blocks select 25/265 audio-window positions beyond the supplied feature tensor and clamp there. The index-level prediction is independently consistent with the [instrumented 10/20-second pair](artifacts/2026-09-25-audio-lookahead-phase/short-pair-validation.json): the first differing block-audio hash was exactly the predicted block 7; predicted pre-encoder frame counts 245/501 also match the saved audits. In the 5/10-second pair, no shared block-audio difference was predicted or observed, and 117/245 predicted pre-encoder frame counts also match.

## Repeated-condition phase and strict comparison windows

The later-block stride is 32 output frames. A 30-second canonical audio-feature period is 720 frames, so its three period starts have phases **0, 16, 0 modulo 32**. The 30- and 60-second audio boundaries lie within different block-grid positions; the [90-s index record](artifacts/2026-09-25-audio-lookahead-phase/period30s-x3.json) identifies crossing audio windows at blocks 22/23 and 45/46. A two-second trim on either side of each period edge removes all crossing-block output around the first boundary, but leaves **five frames (1488–1492)** from a crossing block after the second boundary. This is a small but explicit methodological limit on the previous 2-s-trimmed SyncNet result. The 0.189 full/0.259 trimmed SyncNet declines already fail the prespecified 0.5 signal gate; this phase audit does not explain or reclassify either score.

The early and late periods both have phase 0 yet their SyncNet confidences differ (6.938 versus 6.750), so phase alone cannot account for the measured change. Nor can that residual be assigned to generated-history error without stronger replicated evidence and matched safe windows.

For comparison, a 32-second (768-frame) period repeated three times gives phases **0, 0, 0**, with the same relative block grouping at each period start. The hypothetical [96-s index record](artifacts/2026-09-25-audio-lookahead-phase/period32s-x3.json) has 73 blocks and crossing windows at blocks 24/25 and 48/49; each boundary still leaves five crossing-block output frames outside a naive two-second trim. A [fresh 32-s request](artifacts/2026-09-25-audio-lookahead-phase/period32s-x1.json) would clamp **105/265** positions in its final block, versus 25/265 for the 30-s fresh request, because `int(audio_len/block_duration)+1` adds a partly out-of-range block exactly when the duration is a block-stride multiple. Merely changing the source period to 32 seconds would therefore improve grid alignment **while worsening the naive fresh-control endpoint mismatch**.

If a replicated failure later justifies another costly long run, the protocol should use a naturally available 32-second speech period, exact canonical BF16 feature repetition and a 96-second continuous rollout. It should score only blocks whose entire selected audio window stays inside the intended period, retain pre-encoder frame hashes and mouth/face/motion checks, and provide **guard audio beyond the fresh control's scored horizon** or otherwise decouple conditioning duration from output duration. Those design choices must be frozen before GPU work and applied to all arms. No new 96-second run is justified by the current negative screen.
