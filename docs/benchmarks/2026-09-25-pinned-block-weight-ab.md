# RTX 4090 pageable versus pinned DiT block weights

**Decision:** Keep `--pin_block_memory` optional. At 224×384 it made the three-step later-block median **23.4% faster**, but at the target 416×720 it improved **13.0%**, below the [preregistered 15% promotion gate](../superpowers/specs/2026-09-25-pinned-block-weight-ab-design.md), while reducing sampled host `MemAvailable` by about **25 GiB**. Neither arm approaches 24 generated FPS. This is a measured transfer trade-off using an existing repository flag, not a new quality method or an upstream PR candidate.

## Matched setup and output

All five runs used one RTX 4090 with 62 GiB host RAM, image `examples/image/1.png` (SHA-256 `83f745e79892daf682857aaaf182a9f20748c0f4ffbf03fb527c0ffcf73b76d4`), the exact five-second PCM WAV (SHA-256 `461a35303d0ec2ac87e9d7fda67ecb9fa5ebfd503e5e1b279f2b7c3c19fe8ec0`), prompt `一个人在说话`, seed 42, 24 FPS, three denoising steps, FP8 GEMM/KV, CPU cache and block offload, first-step resident KV, offline FP8/T5 caches, and no compile or latent anchor. The 224×384 pageable arm was run twice; only the pinned arms added `--pin_block_memory`. [The monitored runner](../../benchmark_pin_memory.py) records its exact command, environment and 1-second resource samples in each arm's resource JSON. It terminates a process if host `MemAvailable` is below 8 GiB for two consecutive samples. No run hit that stop.

Every MP4 decodes fully to **117 video frames** (4.875 s) and the same **4.864-s** encoded audio. Audio decoder MD5 is identical across arms (`d563c557286603ae3901699bdbbcecc2`). The [machine-readable summary](artifacts/2026-09-25-pin-memory-ab/summary.json) links the five playable videos, exact requests, logs and resource records. The two [six-timepoint sheets at 224×384](artifacts/2026-09-25-pin-memory-ab/liveact-pin-ab-224-contact.png) and [416×720](artifacts/2026-09-25-pin-memory-ab/liveact-pin-ab-416-contact.png) show no gross new visual defect in the sampled frames. They cannot establish long-form, lip-sync or perceptual equivalence.

Later-block medians exclude block 0, whose source-page faults and other startup effects vary. The pageable 224×384 repeat agrees within 0.4% on this median despite its much slower first block. Pinned improves the 224×384 median by **23.38%** (1.305×), and the 416×720 median by **13.02%** (1.150×). GPU footprint is unchanged at the 1-second sampling resolution. Host `MemAvailable` is a machine-wide measure that includes reclaimable cache and background activity, so its difference is a practical headroom observation, not a precise pinned allocation size. Startup-to-ready also varied with file-page warmth and is not part of the steady-block speed claim.

## Output equivalence and profiling

The videos are **not bitwise equal** after decoding. At 224×384, full-video pageable-versus-pageable-repeat PSNR/SSIM is **29.966 dB / 0.9284**, while pageable-versus-pinned is **30.009 dB / 0.9375** and pageable-repeat-versus-pinned **30.582 dB / 0.9435**. At 416×720, pageable-versus-pinned is **31.189 dB / 0.9473**. The same-arm variation is as large as the cross-arm variation at 224×384, so the A/B does not isolate a pinned-specific image change. It also does not prove exact numerical equivalence or natural motion quality. The fixed seed and decoded-frame mismatch warrant a separate determinism investigation before making any exact-output claim.

That [subsequent diagnostic](2026-09-25-fixed-seed-determinism-diagnostic.md) localized the same-arm cross-process mismatch to Wav2Vec and VAE outputs before DiT, controlled on this setup by disabling cuDNN benchmark. The pinned-weight timing result remains valid, but a future exact-output or quality A/B should set the new reproducibility flag in **both** arms.

A fresh same-code PyTorch profiler pair at 224×384 used the first DiT forward of the second block with a 1.5-second WAV (SHA-256 `bc664bede97fa844a8876837d97c175d35dc78aed2fbd5de2f5aef31efeac177`). The [pageable](artifacts/2026-09-25-pin-memory-ab/liveact-profile-fresh-pageable-224x384-summary.json) and [pinned](artifacts/2026-09-25-pin-memory-ab/liveact-profile-pinned-224x384-summary.json) summaries, [pageable trace](artifacts/2026-09-25-pin-memory-ab/liveact-profile-fresh-pageable-224x384-trace.json.gz) and [pinned trace](artifacts/2026-09-25-pin-memory-ab/liveact-profile-pinned-224x384-trace.json.gz) preserve the attribution. `liveact/weight_copy` contains 2,280 calls in both arms: its reported CPU total falls **1,801→31.5 ms**, while its CUDA range total falls **1,191→971 ms**. The 492 FP8 linear calls retain similar CUDA range totals (**368→357 ms**). The instrumented DiT forward wall is **1.988→1.030 s**. The CPU range difference is consistent with pageable `copy_(non_blocking=True)` still stalling the host, whereas pinned source tensors let the host enqueue copies faster. These profiler ranges are nested and overlap; none should be summed into an exact block decomposition.

For the Vivix JD, this is evidence of a concrete **compute/memory/quality evaluation**: target the measured transfer path, hold the diffusion schedule fixed, and report that an available optimization gives useful low-resolution speed but weak target-resolution speed per host GiB. At 416×720, 1.935 block-only FPS remains about **12.4×** below a 24-FPS stream, before setup and encoding. The high host-memory cost and missing long-run audiovisual equivalence mean this flag should not become the default from this experiment. No identity holdouts or 30-second quality claim were made because the target-resolution performance gate failed.
