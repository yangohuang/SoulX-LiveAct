# LiveAct single RTX 4090 benchmark — 2026-09-23

## Clean upstream comparison (2026-09-24)

To distinguish an upstream feature from this branch's contribution, we ran
unmodified SoulX commit `ac8579b907756f228e975922a5159765c93c6a34` in
a separate worktree on the same RTX 4090/64 GB RAM host. Both attempts used
the same 416×720, 24 fps image, prompt, and 0.5-second audio fixture as the
one-block test below. The host had 2 GB swap, already mostly occupied, and
other host-memory activity; these are results for this machine, not a general
claim that upstream can never run on a 4090.

| Unmodified upstream command flags | Result before generation | Wall time | Process maximum RSS |
| --- | --- | ---: | ---: |
| README 4090 flags: `--fp8_kv_cache --block_offload --t5_cpu` | CUDA OOM while constructing CLIP: a 978 MiB allocation was requested with only 839 MiB free | 5:49 | 34.2 GiB |
| The same, plus existing upstream `--offload_cache --fp8_gemm` | Linux OOM killer terminated Python after checkpoint and VAE loading, before video generation | 7:54 | 52.8 GiB |

The first configuration places all three FP8 KV steps on the GPU. The second
uses upstream's existing CPU KV offload and FP8 GEMM switches, but still
loads BF16 DiT weights before T5 and retains overlapping host allocations
during initialization. The kernel log identifies the second Python process
as the global-OOM victim. Raw logs are
`/tmp/liveact-clean-upstream-4090-{readme,existing-flags}.log` on the test
machine. Neither attempt reached a DiT forward, so these runs establish an
initialization problem, not an upstream steady-state FPS baseline.

The successful BF16/FP8 tests below used a modified local branch, not clean
upstream. A first no-offline-cache retest of the review branch ended with
SIGTERM during startup after 1:35; its result was inconclusive. A subsequent
retry of the same command succeeded from a clean review-branch worktree,
without offline FP8 or prompt caches. It took 7:12.85 wall time, peaked at
54,220,556 KiB process RSS (51.7 GiB), and spent 138.4 seconds on T5,
211.0 seconds on FP8 quantization, and 24.85 seconds on its first generation
block. Its H.264/AAC output has 14 video frames (0.583 seconds) and 0.5
seconds of audio; both streams passed full FFmpeg decode. This is a
same-input *completion* comparison, not a steady-state speed comparison:
neither clean-upstream run reached a DiT forward. The review-branch retry
used `--disable_compile` in addition to upstream's second configuration;
that flag is not present in clean upstream. Its raw log is
`/tmp/liveact-local-review-4090-no-cache-retry.log` on the test machine.

The review branch's cached 1.5-second integrated smoke test and longer 4090
runs are recorded in the separate profile/cache report. The local environment
lacks `flash-attn`; successful generation tests used the CLIP SDPA fallback
from independent PR #19, which is not part of this branch.

## Environment and input

- RTX 4090, 24 GB VRAM; 64 GB host RAM; PyTorch 2.8.0+cu128.
- 416×720 output at 24 fps, seed 42, supplied `examples/image/1.png` and the first 1.5 seconds of `examples/audio/1.wav`.
- Audio excerpt: `ffmpeg -y -i examples/audio/1.wav -t 1.5 -acodec pcm_s16le /tmp/liveact-416-two-blocks.wav`.
- Input JSON uses prompt `一个人在说话`, `cond_image` pointing to the supplied image, and `cond_audio` pointing to that excerpt.
- One 0.5-second excerpt was also used for a single-block comparison. The BF16 and FP8 single-block tests used the same input and settings except `--fp8_gemm`.

## Reproduction

```bash
USE_CHANNELS_LAST_3D=1 CUDA_VISIBLE_DEVICES=0 python generate.py \
  --size '416*720' \
  --ckpt_dir checkpoints/LiveAct \
  --wav2vec_dir checkpoints/chinese-wav2vec2-base \
  --fps 24 \
  --input_json /tmp/liveact-416-two-blocks.json \
  --fp8_gemm --fp8_kv_cache --offload_cache \
  --block_offload --t5_cpu --disable_compile --dura_print
```

The `/tmp/liveact-416-two-blocks.json` file is:

```json
[{"prompt":"一个人在说话","cond_image":"examples/image/1.png","cond_audio":"/tmp/liveact-416-two-blocks.wav"}]
```

## Measurements

| Configuration | First block | Second block | Cold start to MP4 | Peak GPU process memory | Lowest host MemAvailable | Peak process RssShmem |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| BF16 blocks, FP8 CPU KV, 0.5 s audio | 629 s | — | about 13 min | about 6.9 GiB | not recorded | not recorded |
| FP8 blocks, asynchronous GPU→CPU KV, 1.5 s audio | 23.6 s | 17.0 s | 450.5 s | 8,982 MiB | 1,775 MiB | 32,226 MiB |
| FP8 blocks, synchronous GPU→CPU KV, 1.5 s audio | 23.4 s | 21.5 s | 456.0 s | 8,982 MiB | 14,068 MiB | 18 MiB |

The 0.5-second FP8 single-block test took 24.5 seconds after loading, versus 629 seconds with BF16 blocks: about 25.7× faster for the same short input. The final 1.5-second test produced a 416×720 H.264/AAC MP4 with 38 video frames and a 1.584-second container duration. Both audio and video streams passed full `ffmpeg` decode, and a frame from the second block was inspected visually.

For the same 0.5-second input and seed, the 14 encoded output frames from the BF16 and FP8 runs measured 38.24 dB average PSNR and 0.9748 SSIM using FFmpeg. One short clip and these pixel metrics cannot establish perceptual quality or lip-sync equivalence; they only show that this sample did not diverge grossly.

The final two-block run's process high-water RSS was 55,458 MiB. That number includes mapped checkpoint pages; `MemAvailable` captures the host's practical headroom. `RssShmem` is the shared-memory field in `/proc/<pid>/status`, not the broader shared field in `/proc/<pid>/statm`. GPU memory and host memory were sampled every three seconds, so brief peaks may be missed. The prior asynchronous GPU→CPU copy made each returned cache tensor pinned, generating roughly 32 GiB of shared pages during streaming. Blocking GPU→CPU copies prevent that accumulation, at a roughly 4.5-second cost on the second block. CPU→GPU prefetch remains asynchronous.

## Longer local validation (2026-09-24)

The same image, prompt, flags and resolution were run with a 5.000-second excerpt of `examples/audio/1.wav` (`ffmpeg -y -i examples/audio/1.wav -t 5 -acodec pcm_s16le /tmp/liveact-local-5s.wav`). Use the reproduction command above with `--input_json /tmp/liveact-local-5s.json`, containing the same JSON except `cond_audio` points to `/tmp/liveact-local-5s.wav`. Four consecutive blocks cost 24.90, 21.50, 21.43 and 21.37 seconds; the cold start through MP4 completion took 465.1 seconds. The output contains 117 frames at 24 fps (4.875 seconds) with H.264 video and AAC audio, and both streams decoded fully. A late frame was inspected. Sampled minimum host `MemAvailable` was 13,641 MiB and sampled whole-device GPU use peaked at 8,826 MiB. During the four-block generation interval, available host memory moved from about 14,200 MiB to 13,641 MiB. This establishes four-block operation, not hour-scale stability; the 5-second sampler used `/proc/<pid>/statm`, so its shared field is not comparable to the `RssShmem` column above.

The 1.5-second MP4 contains 38 output frames after audio muxing, but generation spends about 44.9 seconds on two complete blocks. Thus 38/44.9 = 0.85 is an *output-frames-per-generation-second* figure for that short clip, not the model's untrimmed frame throughput. The 5-second run gives 117/89.2 = 1.31 output frames per generation second; each later 32-frame block takes about 21.4 seconds, or about 1.5 generated frames per second. Cold start is roughly 7.6 minutes because T5 encoding, BF16 checkpoint loading, and on-the-fly FP8 conversion happen on every process launch. These measurements do not support a real-time claim on this single RTX 4090.
